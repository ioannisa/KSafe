# Alternatives & Comparison

The competitor columns describe each library as it was when this page was last reviewed; check their own changelogs before relying on a ❌.

**Reading the table:**

- *KMP support* — Kotlin Multiplatform: one Kotlin codebase compiled for several targets at once. The row says which targets a library can be used from.
- *Hardware-backed keys* — the key that encrypts your values is created and kept by the platform's own key service rather than by your app, so the stored file on its own decrypts to nothing. On Android that service is the Keystore, on iOS and macOS the Keychain; both are backed by a security chip where the device has one. The chip holds a wrapping key that never leaves it, and the working key it wraps is unwrapped into your app's memory to do the encryption — so this stops a stolen disk, a backup or another app, not an attacker who can read the memory of your running app. On JVM Desktop the key sits in the OS credential store instead (Windows DPAPI, the macOS login Keychain, the Linux Secret Service), and on the web in a `CryptoKey` marked *non-extractable* — the browser will use it but never hand its bytes to JavaScript — kept in IndexedDB, the browser's local database. Those last two protect against another user of the machine or a stolen disk, not against code running inside your own app, and KSafe reports them on its own protection-level scale as `SANDBOX_PROTECTED` rather than `HARDWARE_BACKED`. `ksafe.protectionInfo` tells you which case you actually got — see [PROTECTION_INFO.md](PROTECTION_INFO.md).
- *Zero boilerplate* — `var token by ksafe("")`: the property name becomes the storage key, the default's type becomes the value type, and reading or assigning the property reads or writes the store. The default is also what you read back while nothing is stored under that key. Since 3.2.0 the same call also works without the delegate, as long as you name the key yourself: `val counter = ksafe(0, key = "counter"); counter.value++`.
- *Key rotation* — replacing the encryption key and re-encrypting everything it protects, so a key that leaked stops being useful. See [KEY_ROTATION.md](KEY_ROTATION.md).
- *Biometric helper* — `KSafeBiometrics.verifyBiometric()`, a `suspend` function (one that can wait without blocking the thread) returning `true` when the user passed the Face ID / Touch ID / fingerprint / Windows Hello / passkey prompt, and `false` when they failed or dismissed it. On the web the prompt goes through WebAuthn, the browser's passkey standard. Where the platform offers no prompt at all — Linux desktop, the iOS Simulator, or a browser with no built-in authenticator while the default `allowDeviceCredentialFallback = true` is in force — it returns `true` without prompting, so shared code needs no branching. Call `KSafeBiometrics.biometricsAvailable()` first when a silent pass would be unacceptable. See [BIOMETRICS.md](BIOMETRICS.md).
- *Compose state* — `:ksafe-compose` adds `ksafe.mutableStateOf(...)` for a class or ViewModel property and `ksafe.rememberKSafeState(...)` for use inside a `@Composable` body. Both give you Compose state whose value lives in KSafe, so every changed assignment redraws the UI *and* persists. `mutableStateOf` writes encrypted by default; `rememberKSafeState` writes plain unless you pass a `mode`.
- *Type safety* — reified generics: the Kotlin feature that lets `ksafe(0)` know at the call site that the value is an `Int`, so there are no casts and no type names spelled out as strings.
- *Auth caching* — `verifyBiometric(authorizationDuration = BiometricAuthorizationDuration(duration = 60_000L, scope = "payments"))`: later calls in that scope skip the prompt for 60 seconds. The duration is in milliseconds; separate scopes keep separate timers, and `KSafeBiometrics.clearBiometricAuth("payments")` ends one early.
- *Operational preflight* — `ksafe.protectionInfo.isEncryptionOperational`, a startup check answering "will encrypted reads and writes succeed right now?". It is `false` in exactly two situations: a web page served outside a *secure context* (HTTPS, or a `localhost` origin), where the browser withholds its crypto API, and a Desktop whose OS credential store exists but cannot be reached (a locked keyring, a headless launch). A weaker-but-still-working fallback reads `true`.

**Browser support, specifically:** KSafe ships two web artifacts built from the same source — a Kotlin/Wasm build (WasmGC, the newer WebAssembly runtime that recent browsers ship) and a Kotlin/JS build for older browsers. Both keep values in `localStorage`, the browser's per-site key-value store, and encrypt them with AES-GCM — a standard algorithm that both encrypts a value and detects any later tampering with it — using a 256-bit key by default, or 128-bit if you configure it. The encryption runs through WebCrypto, the browser's built-in crypto API, with the key held as a non-extractable `CryptoKey` in IndexedDB, so you can switch between the two targets without losing data. WebCrypto only works asynchronously, so a web store decrypts its values in a background preload: call `ksafe.awaitCacheReady()` once at startup, before the first non-suspending read (`getDirect`, a `by ksafe(...)` property, Compose state). The suspending `get()` waits on its own. Encryption needs that secure context (HTTPS, or a `localhost` / `127.0.0.1` origin); anywhere else `isEncryptionOperational` is `false` and encrypted reads and writes fail. See [SETUP.md](SETUP.md) and [ARCHITECTURE.md](ARCHITECTURE.md) for details.

**When to choose KSafe:**

- You want one dependency for both plain preferences and encrypted secrets. Every write picks a mode: `KSafeWriteMode.Plain` stores the value as-is, `KSafeWriteMode.Encrypted()` encrypts it, and on Android and iOS/macOS you can ask for `KSafeWriteMode.Encrypted(KSafeEncryptedProtection.HARDWARE_ISOLATED)` — StrongBox or the Secure Enclave, a security chip physically separate from the main one. Where the device has no such chip, and on Desktop and web, that write silently lands in the regular encrypted tier; `ksafe.getKeyInfo(key)?.level` reports where the key for that entry actually landed.
- You need encrypted persistence across Android, iOS, macOS, Desktop and Web from a single API in `commonMain`, the shared source set every target compiles.
- You want minimal boilerplate. A stored value reads and writes like an ordinary variable — `var token by ksafe("")`, or the delegate-free handle shown above — with no editor object, no `apply()`, and no separate key constants.
- You need a biometric gate in shared code. One `KSafeBiometrics.verifyBiometric()` call raises the platform's own prompt, and an authorization duration keeps the following calls in that scope prompt-free. See [BIOMETRICS.md](BIOMETRICS.md).
- You use Compose and want state that persists: `var token by ksafe.mutableStateOf("")` in a ViewModel, or `var name by ksafe.rememberKSafeState("")` inside a composable, both from `:ksafe-compose`. Assigning the property updates the UI and saves in the background. See [USAGE.md](USAGE.md).
- You need key rotation. Some security standards require an encryption key to be replaced on a schedule, and a fresh key limits how much a leaked one can still decrypt. `ksafe.rotateKeys()` re-encrypts every encrypted entry under a new *key generation* — a numbered set of keys, recorded on every entry, so a store can hold several at once — and deletes the keys it supersedes (plaintext entries have no key, so they are untouched). It is a `suspend` call that runs in your own coroutine, so start it from a background one on a large store. `KSafeKeyRotationPolicy.MaxAge(90.days)` in `KSafeConfig` does the same automatically, in the background shortly after startup, once the key is older than the limit. Every entry stays readable while a rotation runs. See [KEY_ROTATION.md](KEY_ROTATION.md).
- You want tamper-evident storage. From the first rotation on, each encrypted entry is cryptographically bound to its store, its key name, its protection tier, whether it was written to require an unlocked device, and its key generation — the "authenticated envelope". An entry copied into another store, renamed, or re-tagged as a different tier no longer decrypts, and the read returns the default you passed. Whatever an attacker with file access does to the stored bytes or their metadata, the secret itself is never handed back. Rotation is off by default (`keyRotationPolicy = KSafeKeyRotationPolicy.Never`), so call `rotateKeys()` once to switch this on. Details in [KEY_ROTATION.md](KEY_ROTATION.md).
- Performance matters. On the Android benchmark device, KSafe read encrypted values about 2.6× faster than KVault even while decrypting on every single read, and its fire-and-forget encrypted write — one that returns as soon as the value is queued, with the disk commit following — was about 383× faster; see [BENCHMARKS.md](BENCHMARKS.md) for the tables, the device, and the version they were measured on.

**When to consider alternatives:**

- You need complex queries → Consider SQLCipher or Room with encryption
- Android-only app with simple needs → EncryptedSharedPreferences works
- No encryption needed → Multiplatform Settings is lighter
- Plain preferences on Android, iOS/macOS or Desktop with no encryption → Jetpack DataStore, Google's key-value file store, is lighter on its own. KSafe uses DataStore as its file layer on those platforms and adds encryption, property delegates, Compose state and the biometric gate on top; if you need none of those, you do not need KSafe.
- Simple KMP encryption needs → KVault is a good alternative; it decrypts on every read through the platform key service, so reads cost more than KSafe's (see [BENCHMARKS.md](BENCHMARKS.md))
